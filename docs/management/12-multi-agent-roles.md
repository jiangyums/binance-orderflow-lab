# 12. 多 agent 角色模型

> 状态：生效

本文件定义项目中多 agent 协作时的角色模型、权限边界与参与者对应关系。

## 1. 角色分类

当项目中出现多个智能体协作时，必须明确每个角色的职责、权限和边界。

规则：

- 每个状态变化都必须记录具体角色和参与者。
- 每个角色只允许执行与其职责直接相关的动作。
- 角色不是“人”，而是“可绑定到具体参与者的职责标签”。
- 角色之间的权限不能互相吞并；将设计、实现、审查、验证混在一起会导致责任不清。

## 2. 角色表

| 角色标签 | 含义 | 主要职责 | 默认参与者 | 写权限 |
|---|---|---|---|---|
| `PM` | 项目经理 / 审批人 | 审批方案、输出审批结论、审批任务 | Cline | 只读审批 + 落盘即提交（任务台账与本角色审批报告，依 `14` §6.0） |
| `Architect` | 架构师 | 需求分析、接口设计、方案制定、任务提出 | Qoder | 仅在已获批任务范围内；落盘即提交（依 `14` §6.0） |
| `Coder` | 代码编写者 | 落地实现、生成代码、修改工作区文件 | opencode | 仅在已批准任务范围内；落盘即提交（依 `14` §6.0） |
| `Tester` | 测试者 | 编写测试、验证产物、做验收 | kilo | 仅在已批准任务范围内；落盘即提交（依 `14` §6.0） |
| `Reviewer` | 审查员 | 独立审查方案、接口、风险 | VS Code Copilot | 只读审查 + 审计报告 / 台账落盘即提交（依 `14` §6.0） |

> 各角色 git 提交/推送遵循 `14` §6.0「落盘即提交」：仅对本角色被允许落盘的那批文件（及对应任务台账）执行 `git add` / `git commit` / `git push`。

## 3. 角色边界

### 3.1 PM（项目经理 / 审批人）

- 职责：
  1. 根据 Reviewer、Tester 的输出结果进行审批。
  2. 审批项目治理文档（其文本由 Coder 依已批准设计落盘）。
  3. 审批其余的文档和代码。
  4. 对审计意见逐条核对，明确标注“修复”“无视”“延后”。
  5. 补充未被审计的领域，指出“应当被审计”的对象。
  6. 审批结论必须使用四态：`approved / rejected / blocked / deferred`；不得使用“有条件通过”“部分通过”“通过但需补充”等非四态结论。
- 禁止：修改未经审批的实现/代码文件。
- 允许：写入任务台账 `tasks/T-YYYYMMDD-NNN.md` 的 `status` 行与状态记录行，以及落盘本角色审批报告 `tasks/T-YYYYMMDD-NNN/<阶段>-approval-report.md`（每审批段一份，见 `14` §6.2），并依 `14` §6.0「落盘即提交」对上述文件执行 `git add` / `git commit` / `git push`（见 `agents/pm.md` §5）。
- 允许：阅读文件、检索代码、输出审批意见。
- 输出：
  - 审批结论：四态之一；
  - 审批报告：落盘到 `tasks/T-YYYYMMDD-NNN/<阶段>-approval-report.md`（每审批段一份，命名对照见 `14` §6.2）。

### 3.2 Architect

- 职责：整理需求、提出任务、设计方案、明确输入/输出契约。
- 禁止：在未获得 `proposed-approved` 前直接将项目提案文档（需求说明）标记为 approved。
- 禁止：在未获得 `designed-approved` 前直接将设计文档标记为 approved。
- 禁止：将任何文档或任务状态标记为 approved（approved 系列状态由 PM 根据审批结论触发）。
- 允许：提交项目提案或需求说明，将任务置为 `proposed`。
- 允许：提交设计文档，将任务置为 `designed`。
- 允许：执行跨段回退 `designed-rejected → proposed`、`build-reviewed-rejected → designed / proposed`、`build-verified-rejected → designed / proposed`（PM 判「设计 / 需求无法满足」时；见 `14` §7.1、`13` §3.2）。
- 说明：获得 `designed-approved` 后，任务进入交付段（`build`）；该转移由 **Coder** 执行（见 `13-task-model.md` §2.3）。

### 3.3 Coder

- 职责：落地已批准任务的实现。
- 禁止：修改未批准任务的文件；不得绕过审批直接改动一般实现文件。
- 允许：直接落地已批准任务的实现代码。
- 允许：落盘由当前任务 `output_contracts` 指定的交付物文件（含代码与文档，含项目治理文档）。
- 约束：文本与逻辑须由已批准设计确定，不得自行发明；项目治理文档的文本由 Coder 落盘、生效由 PM 审批（见 `14` §5.1）。

### 3.4 Tester

- 职责：依据已生效的设计文档对代码进行测试，交付测试结果（对应测试线 `build-reviewed-approved` → `build-verified`）。
- 禁止：不提出解决方案，不修改未批准的实现/生产代码。
- 允许：编写测试用例、运行测试、生成测试报告。
- 允许：读取已生效的设计文档、实现代码和测试产物。

### 3.5 Reviewer

- 职责：依据已生效的文档对代码和文档进行审查，在代码测试以外的领域找到问题（对应三段审计线：`proposed-reviewed` 提案审计、`designed-reviewed` 设计审计、`build-reviewed` 交付审计）。
- 禁止：不提出解决方案，不直接落地实现。
- 允许：审查代码、文档、接口、风险、设计合理性。
- 允许：提出问题和需要修正的地方，但不提供实现方案。
- 允许：设计审计时（`designed → designed-reviewed`），审查设计是否能够达到项目提案（需求）目标。考核维度包括技术可行性、经济可行性（依赖的软硬件、服务是否可获取且在预算内）、时间可行性。
- 允许：交付审计时（`build → build-reviewed`），审查实现是否能够达到技术方案目标。考核维度包括技术可行性、经济可行性（依赖的软硬件、服务是否可获取且在预算内）、时间可行性。
- 允许：审查结束、提交审查报告时，将任务置为对应审计状态（`proposed-reviewed` / `designed-reviewed` / `build-reviewed`）。
- 允许：在审计报告中明确“审计覆盖范围”，包括已覆盖对象、文件、领域，以及“审计覆盖缺口”（未覆盖对象、未覆盖原因、建议后续审计对象与完成时间），以便 PM 做后续补审。

## 4. 角色标签与参与者映射

角色标签用于状态记录和任务字段。

| 角色标签 | 默认参与者 | 说明 |
|---|---|---|
| `PM:Cline` | Cline | 审批人 |
| `Architect:Qoder-A` | Qoder | 架构师 |
| `Coder:opencode` | opencode | 代码编写者 |
| `Tester:kilo` | kilo | 测试者 |
| `Reviewer:copilot` | VS Code Copilot | 审查员（加载入口 `.github/agents/reviewer.agent.md`） |

> 参与者 ID 具体可以是工具名、智能体名或用户标识。

## 5. 最小变更约束

1. 不删除或覆盖现有 `PM` / `Qoder` 职责。
2. 新增角色只作为可选扩展，不强制所有新任务都使用这些角色。
3. 所有新角色记录必须基于已有任务或明确提出的任务。
