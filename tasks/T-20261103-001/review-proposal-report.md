# T-20261103-001 提案审计

## 发现

### P1 — `has_code` 的核心判定依据不足以一致复核

提案目标一要求 Architect 依据 `output_contracts` 成员类型声明 `has_code`，§4 己又将交付审计中的成员类型复核作为防止绕过测试的控制；但提案没有界定哪些交付物类型构成“含代码”。当前文本无法据此一致判断源代码、测试代码、脚本、配置／生成物，或文档内代码内容是否计入。该判定直接决定是否免除测试线，标准不明确会使同一类任务可能被不同参与者赋予相反值，核心分支及其防绕过控制因而不可稳定验证。

### P2 — 时间可行性及在治任务的时序无法确认

提案指出 `T-20261102-001` 已到 `build-reviewed-approved`，而新规则可能影响其后续结案；同时列出多项须裁事项及多载体一致性范围。但提案未给出工作量／周期估算，也未明确与该在治任务测试线的先后关系。时间可行性及规则生效能否赶在关联任务结案前，无法由现有材料确认。

## 审查判断

- **技术可行性：** 变更以治理文本、台账字段和状态规则为主，不依赖新增运行时软件；所识别的状态机缺口有现行规则和实例支撑。核心 `has_code` 判定标准未定义，导致免测试分支尚不能被一致执行和审计。
- **经济可行性：** 未发现新增软硬件、付费服务或外部数据依赖；提案已识别公开仓库披露风险，未发现额外预算因素。
- **时间可行性：** 变更载体多且须处理多个待裁事项；提案说明了关联任务的时间敏感性，但没有量化安排，当前无法确认工期或生效先后。
- **总体判断：** 提案所针对的任务终态缺口真实且具有处理价值；`has_code` 的认定边界是影响主目标和防绕过控制的 P1 缺项。时间安排亦待明确。上述判断供 PM 审批参考，不构成四态审批结论。
