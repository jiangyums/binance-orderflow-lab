# T-20261103-001 设计审计

## 审计覆盖范围

- 对象：`tasks/T-20261103-001/design.md`、任务台账，以及前置提案审计和审批报告。
- 对照：`AGENTS.md` §2、§4；`docs/management/12-multi-agent-roles.md` §3.2–§3.5；`docs/management/13-task-model.md` §2、§3、§4、§5、§6、§7、§8；`docs/management/14-responsibility-boundaries.md` §5.1、§6.0、§6.5、§9；`docs/management/15-version-control-convention.md` §4.2–§4.3、§5.2。
- 方法：核对设计对提案审计和审批意见的响应、状态机与终态语义、变更载体和验收判据、关联任务及治理文档生效时点；评估技术、经济与时间可行性。
- 前置核验：提案审计报告、提案审批报告及相应状态记录均存在；任务台账状态为 `designed`，设计稿已落盘。

## 发现

### P1 — 免测试任务沿用审批态，未解决终态与中间态混用

设计选择将 `build-reviewed-approved` 同时作为 `has_code = false` 任务的终态，以及 `has_code = true` 任务进入测试线前的审批状态（M-8、M-9、M-12、M-25）。因此仅看 `status` 时，同一状态既可能表示任务已完成，也可能表示任务仍须进入 `build-verified`；需要再结合 `has_code` 才能判定是否结束。状态图中的「任务完成（final）」只是图示标签，并非新增的状态值或状态转移。设计虽列举复用与新建终态两种选项，却未评估独立任务结束标记对终态可辨识性及状态记录语义的影响，也未回应用户提出的专门结束标记问题。

### P1 — 任务完成与治理文本生效的时点不一致

M-16 说明治理文本须经用户批准后生效；M-25 却规定 `has_code = false` 的任务在 PM 批准 `build-reviewed` 后即完成。设计没有界定两者之间任务台账的状态和责任，也未说明用户批准若尚未发生或未通过，任务是否已完成、治理文本是否仍待生效。因而状态所表达的“任务完成”与该任务治理交付物的生效结果可能不一致；此处又被列为未重开的既存流程余量。

### P2 — 时间可行性仍无法判断

设计给出了 M-1～M-27 的依赖顺序及单次交付安排，但未提供可核验的工作量或周期估算。缺少历史工时数据可以解释不采用精确人日估值，却仍不足以判断多载体变更、审查和治理批准所需时间，以及与两个在治任务结案时间的相容性。

### P2 — 部分机械验收判据的复核依据不明确

J-2、J-6 将清单数量、扫描命中数及处置数描述为脚本计数，但设计未指明相应脚本或其可复核载体；J-6 还含有“须么带”这一无法明确解析的措辞。当前无法仅依设计稿唯一确定这些检查的执行依据及全部合格条件，降低判据的可重复核验性。

## 审查判断

- **技术可行性：** 变更以治理文本、台账和角色手册为主，不依赖新增运行时软件。提案审计 P1 中的 `has_code` 成员类型判定边界已由 §5.2 的清单和缺省规则予以回应；但终态与中间审批态重用、以及治理文本生效与任务完成的时点差异仍未闭合，直接影响任务状态机的可判定性。
- **经济可行性：** 未发现新增软硬件、付费服务或外部数据依赖；未提供预算数据，但设计未显示直接采购成本。
- **时间可行性：** 交付顺序明确，但无量化时间依据，不能确认计划周期。
- **总体判断：** 设计覆盖面较完整，`has_code` 判定规则及跨载体同步已有具体文本；然而两个 P1 影响“任务何时、以何状态结束”的核心语义，当前状态值不足以仅凭状态辨别完成与继续测试，且治理交付的生效时点另有待定。上述问题供 PM 审批参考，不构成四态审批结论。

## 审计覆盖缺口

- 尚未审计实际治理文档交付；M-1～M-26 尚未进入 build，跨载体实现及实际文件集只能在交付审计中核对。
- 未评估用户批准治理文本的实际等待时间，也未审查用户不批准时的任务状态处理。
- 未验证设计所称脚本计数；当前未提供脚本产物或可直接复现的执行记录。
- `T-20261020-001` 与 `T-20261102-001` 的结案裁定仍待处理；本审计不代替 PM／用户作该裁定。
