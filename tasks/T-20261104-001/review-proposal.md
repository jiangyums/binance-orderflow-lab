# T-20261104-001 提案审计

## 审计覆盖范围

- 对象：任务台账与 `tasks/T-20261104-001/proposal.md`。
- 对照：`AGENTS.md`；`docs/management/12-multi-agent-roles.md` §3–§4；`docs/management/13-task-model.md` §2、§3.2、§3.3、§3.4；`docs/management/14-responsibility-boundaries.md` §6.4–§6.5；`agents/architect.md`。
- 方法：核对提案对「用户指令效力」「代为继续」「角色动作边界」的定义是否能在单一文本上得到唯一解释；比对提案所宣称的派生规则与现行状态转移／角色权限是否自洽；检查提案是否真正覆盖核心场景并可证明拒绝/允许边界。
- 前置核验：本审计基线为任务台账当前 `proposed` 状态，且提案已在本轮返工后更新；审计对象为当前工作树中的提案文本，不对历史版本做更改。

## 发现

### P1 — 提案仍未给出“用户指令”与“禁止转移”的优先级，核心场景仍不可唯一判定

提案在 §4 中区分了两层：甲层定义用户指令的效力、乙层定义角色侧的动作边界，并声称二者不互斥；但它仍未给出清晰的优先顺序：当用户要求“在 `build` 阶段让 Architect 重做设计”时，究竟是被视为合法输入并触发代置，还是被认定为越出当前状态权限并受 `13` §3.3 禁止转移规则制止？

这点没有被写明，导致核心问题依旧保留：同一条用户命令在当前文本中仍可能被同时解读为（a）合法的“代为继续”，以及（b）被禁止的表外转移。提案有意把「用户指令」与「状态机规则」拆成两层，但没有定义两层之间的判定顺序；因此，审计线仍无法按单一规则判定该场景的最终动作。

这不是理论问题，而是提案所宣称要覆盖的实际争议场景：在 `build` 状态下，架构师收到越出当前权限的用户要求时，应如何处理，仍没有唯一结论。

### P2 — 提案宣称“单一载体可读”，但仍依赖跨文件引用和非自足的派生规则

提案的 J-2/J-6 目标是把「每一状态与执行角色」都做到可从表内唯一读取；但在现行 `13-task-model.md` 中，`13:183` 仍把执行角色的来源指向 `12-multi-agent-roles.md` 和 §4，且 `12` §4 仅体现角色标签/参与者映射，不能直接提供每个转移的执行角色。提案中也未在 `13` 自身形成最终的权威载体，仍需依赖跨文件间接抽取。

这会造成两类问题：

- 当前文件中虽然写明“派生规则”或“单一载体”，但权威文本仍分散在 `12`、`13`、`14` 之间，最终读者依然可能转到不同的引用链。
- 若 `12` / `13` / `14` 的各自解释不一致，J-2/J-6 中的“逐边读数”只会复现同一根因：没有唯一的判定载体。

因此，提案暂时具备“概念方向正确”的迹象，但尚未形成一份能独立执行并可审计的规约文本。

## 审查判断

- 技术可行性：问题确实存在，且提案所定位的争议点真实；但核心优先级与单一权威载体尚未落定，因而目标还不能被可信地验收。
- 经济可行性：本任务仅涉及治理文档和台账文本，不涉及新增软硬件或外部依赖。
- 时间可行性：本提案未提供明确落地拆解和排期，且最核心规则仍未定型，时间估算尚无依据。
- 总体判断：提案值得继续讨论，但在当前形态下不满足“可验证的治理规则”要求；建议返工后重审。

## 审计覆盖缺口

- 未对“用户明确改令”与“禁止转移”之间的优先级做最终定性；该项是本任务的核心风险点。
- 未在 `13` 自身完成“状态 × 角色 × 动作”的唯一权威表达，因此仍无法证明跨角色／跨阶段指令的全部同类场景都被同一规则覆盖。
- 当前提案仍未提供一条能机械执行的判定句，能够直接回答：「角色 R 在状态 X 下收到越出其当前动作集合的用户要求时，应如何处理？」

## 审计结论

本次提案审计结论：`proposed-reviewed`。

理由：提案指向的真实问题成立，且已明确定位了一类实际缺口；但该问题的关键优先级与最终修订载体尚未收口，仍不足以形成审计和审批上可执行的唯一规则。相关问题已交回 Architect：需在 `13` / `14` / `12` 的最终文本中明确用户指令与禁止转移的优先级，并给出唯一权威的状态-角色-动作判定载体。
