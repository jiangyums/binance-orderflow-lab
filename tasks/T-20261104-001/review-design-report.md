# T-20261104-001 设计审计

## 审计覆盖范围

- 对象：`tasks/T-20261104-001/design.md` 与任务台账。
- 对照：`tasks/T-20261104-001/proposal.md`、`tasks/T-20261104-001/proposal-approval-report.md`、`docs/management/13-task-model.md` §2–§7、`docs/management/14-responsibility-boundaries.md` §6.4–§6.5、`docs/management/12-multi-agent-roles.md` §3–§4、`AGENTS.md` §2–§4。
- 方法：核对设计方案是否在单一文本中给出唯一的状态-角色-动作判定；检查是否覆盖 PM/Reviewer 返工要求的关键场景；复核其是否能在不伤及既有治理文本的情况下落地并可审计。
- 前置核验：任务已进入设计段，设计稿已落盘；本次审计针对当前工作树中的设计稿，不对历史提交做改写。

## 发现

### P0 — 设计仍然保留“待裁定槽位”，未形成可提交的唯一方案

设计稿第 7 节与第 8 节中明确置出多项必须由 PM/用户裁定的槽位，且这些槽位直接决定了最终治理规则的可执行性：

- 庚：`proposed-rejected → proposed` 是否进入 `13` §3.2 表，还是仅以定义句扩展允许转移全集。
- 辛：`F-1` / `F-2` / `F-3` 三种落点形制如何选定，且此选定直接影响 `13` §12.2 的解释。
- 壬：是否补全 `§6` 交付物表的 9 个阻塞/拒绝/延期状态行。
- 戊：PQ-9 的归口与提交方式。
- 己：已结案任务的基线是否重开或后续另行登记。

这些问题不属于“细节微调”，而是最终治理文本是否成立的关键条件。设计稿将本应在设计阶段确定的规范性选择留给后续裁定，导致当前设计并未形成单一、稳定、可执行的规则集合；对审计线而言，最终判定方式依然不唯一。

### P1 — 设计稿声称“单一权威读法”，但仍保留跨文件指针，并且没有真正消除对 `12` / `13` / `14` 的分散依赖

设计稿在 §2 与 §6 中声明了派生规则 D，并声称将 `13` 自身作为唯一权威载体；但在 §6 的 M-3 与 M-4 中，仍保留了对 `13:183` 与 `14:204` 的原地改句/追加句，说明设计并不能在现状文本上彻底消除跨文件引用依赖。

更关键的是，设计稿本身承认发布前必须达成“辛”裁定：

- 如果裁定 `13` §12.2 不允许句级订正，则只能走纯追加方案；此时 `:183` 的跨文件指针仍然在，J-D2 所要求的“单一载体、无需跨文件指针”无法达成。
- 如果裁定允许句级订正，则可以用 F-3（文末追加节）+ M-3a（同锚改句），但这又取决于治理文档层面的新规则定义，并未在当前设计稿内提前定型。

因此，设计目前仍然停在“可讨论方案”的层面，而不是“已定稿并可落地”的规则文本。它并未真正实现本任务最关键的目标：让状态 × 角色 × 动作的判定在单一载体中稳定成立。

### P2 — 设计稿对 `13:476` 的处理仍然不够严格，无法保证唯一解释

本稿在 §3.3 与 §6 的 M-2 中给出两种可能处理方式：

- M-2a：改写 `:476` 原句。
- M-2b：不改 `:476`，通过 M-1 的优先声明覆盖。

这意味着设计稿中同一条冲突规定允许两种落地路径。且在 §3.3 中，它已承认 `:476` 目前“自相矛盾”（`build-verified` 进入态由 PM 产出，又声明 Tester 只置位 `build-reviewed-approved → build-verified`），但设计并未在当前阶段给出最终唯一选项，只是把它交给进一步裁定。

对审计线而言，这仍然是一个未闭合的核心冲突：最终治理文本对 `build-verified` 的执行角色会因裁定不同而不一致，导致测试线和状态机判定不再唯一。该问题直接关系到 `has_code = true` 任务的合法性与 PM/Tester 权限边界。

### P3 — 设计稿对“用户指令”的效力说法仍与 `14` §6.5 的例外义务冲突，且未写出最终条款排序

设计稿在 §6 M-1 的 §13.3 中写明：

- 用户指令只构成输入，不构成转移；
- 用户改令只能免除“停止等待上一流程完成”的义务；
- 任何指令都不得扩大角色置位权；
- §3.3 与本节优先。

但它仍没有在当前设计中明确：

- 用户改令究竟只是对“流程等待”的豁免，还是也能在跨角色／跨阶段场景中改变某角色的动作集合？
- 如果用户要求某角色执行不在其动作集合中的动作，最终是“拒绝并报告”，还是“允许代置但必须留痕”？

设计稿把这些都写成“判定顺序”与“可读集合”，但未在最终文本中给出唯一的四段落式先后顺序。其结论仍依赖后续 PM/用户裁定，而不是一句可以直接执行的优先级句。

## 审查判断

- 技术可行性：设计方向有价值，且确实指向了真实缺口；但当前版本未达到“单一规范文本”的要求，不能认为已具备落地条件。
- 经济可行性：本任务仅涉及治理文本和台账修改，无需新增外部依赖。
- 时间可行性：设计稿中的未决槽位较多，且每一槽位都对生成规则的最终内容有实质影响，当前无法给出可靠工期与验收边界。
- 总体判断：设计方案存在关键缺口，尤其是“最终优先级句、唯一权威载体、冲突取值处理、裁定槽位收口”四类问题，未达到审计通过标准。建议返工后重审。

## 审计覆盖缺口

- 未给出 `13` / `14` / `12` 三个文档之间单一生效优先级的最终定稿句。
- 未对 `M-2a / M-2b`、`M-3a / M-3b` 形成唯一结论。
- 未完成对 `F-1 / F-2 / F-3` 的最终裁定，导致落点形制依然不稳。
- 未在设计稿内正式关闭 `庚 / 辛 / 壬 / 戊 / 己` 等关键槽位，无法证明当前方案可单一执行。

## 审计结论

本次设计审计结论：`designed-reviewed`。

理由：设计稿已具备较好的问题识别和形式化思路，但在当前工作树中仍没有形成唯一、机械可执行的治理规则；关键决策点被明确留给后续 PM/用户裁定，且有多个可选落地路径。对于本任务的核心目标而言，设计阶段尚未闭环，需在规范优先级、冲突处理和落点形制上进一步收口后重审。
