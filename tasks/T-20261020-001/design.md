# T-20261020-001 设计方案

## 1. 设计目标与范围

把「用户下达创建任务 ＋ Architect 确认已理解需求 ⇒ 任务台账与提案同轮落盘并置 `proposed`」写成可执行规则，
并顺带收敛本次实跑中实测到的台账形制不一致。范围限于 `13-task-model.md`、`15-version-control-convention.md`
两份文本与任务台账字段区；不新增状态枚举，不改状态机转移集。

## 2. 关键设计决定

| # | 决定 | 理由 |
|---|---|---|
| D-A | **不引入** `drafting`／`草案` 可记录态；落盘即 `proposed`，无中间停留态 | 新增枚举会同时牵动 `13` §2 三张状态表、§3.2 允许转移、§3.3 禁止转移、§6.1 成熟度五级、附录 A 对照表共 6 处；而「即时落盘」本身不需要第三种态 |
| D-B | 任务台账的**建立时点＝ `proposed`**，与 `proposal.md` 同轮落盘 | 使「Reviewer 仅凭仓库文件即可接手」有确定载体；建在更早的态会把无转移的时刻写进 append-only 记录区 |
| D-C | 台账首条记录行的旧状态使用字面量 `(新建)`，**仅限该行** | 本次实跑用了 `—>`，它既不在 `13` §2 枚举内，也偏离 `13` §10 的 `->` 形制。需要一个有界例外而不是放行任意旧状态 |
| D-D | 台账字段以 `13` §5 为权威；`15` §4.2 模板补齐；字段区可更新，状态记录区仍 append-only | 实测三处字段集互不相同（见 §3 表 E-3）；`15` §4.3.1 只规定 `status:` 行的更新纪律，未覆盖其余字段，须补许可否则回填即违规 |

## 4. 逐项修订方案

### M1｜`13` §6 交付物表补台账建立时点（D-B）

在表首 `proposed` 行**之前**新增一行：

```markdown
| （任务建立） | 任务台账 | Architect | `tasks/T-XXXX.md` |
```

并在表下注中追加一句：

```markdown
> 任务台账在 `proposed` 置位的同一轮创建，与 `proposal.md` 同轮落盘；建立时即写入首条状态记录行（旧状态取值见 §10）。
```

### M2｜`13` §7.1 收敛触发与动作（D-A）

该节现有两处重复表述（先「用户明确同意提案后置 `proposed`」，后又重述一遍确认属内部规范）。改为一条：

```markdown
用户下达创建任务且架构师确认已理解需求时，架构师在同一轮内创建任务台账 `tasks/T-XXXX.md` 与提案 `tasks/T-XXXX/proposal.md`，并将状态置为 `proposed`；两者同轮落盘，不设草稿专用目录或草稿专用态。正式化之前的对话讨论不落盘任何文件。

用户对提案的确认属于 Architect 的内部工作规范，不进入 PM / Reviewer 的审批链路，不在任务台账中设置单独核对项。
```

删除原句中的 `**隐藏状态 `Drafting proposal`（提案中）**` 表述，改为「正式化之前的对话讨论」——保留隐藏状态语义但不再给它一个似态的名称（`13` §6.3 的同一短语按本条同步替换）。

### M3｜`13` §10 冻结旧状态取值（D-C）

在状态记录格式代码块之后追加：

```markdown
> `<旧状态>` 与 `<新状态>` 的取值域是 §2 三张状态表的全部状态，外加唯一例外：任务台账的首条记录行，其 `<旧状态>` 写作字面量 `(新建)`。除此之外的任何旧状态取值一律非法。
```

### M4｜`15` §4.2／§4.3 对齐字段权威与更新许可（D-D）

§4.2 模板块补至 `13` §5 的 13 项；§4.3 新增第 5 条：

```markdown
5. 字段区（`## 状态记录` 之前的 `- ` 行）随任务演进更新，不受 append-only 约束；append-only 仅适用于「状态记录」区。
```

### M5｜`13` §5 把「至少包含」改为分级必填（D-D 的配套）

```markdown
必填：`task_id`／`title`／`status`／`created_at`／`updated_at`／`revision`／`assignees`／`input_contracts`／`output_contracts`
选填（缺省视为空）：`description`／`dependencies`／`approval_chain`／`risk`
```

## 9. 风险与回滚

- 风险：M3 给「旧状态」开一个有界例外，可能被后续任务扩大解释。缓解：M3 文本已用「除此之外的任何旧状态取值一律非法」封口。
- 风险：M4 放开字段区更新，可能被用来改写 `assignees` 掩盖历史。缓解：字段区改动同样走提交，`git diff` 可追；append-only 只保护状态记录区这一事实写明。
- 回滚：M1–M5 均为整句新增或整句替换，逐句 `git revert` 即可；本任务台账与提案文件不因设计段的采纳而回改。
