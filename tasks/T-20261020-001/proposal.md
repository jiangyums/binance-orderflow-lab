# T-20261020-001 任务创建动作即时落盘

## 1. 需求（仅回答是否值得做）

用户要求创建一个任务、且架构师确认已理解需求之后，任务台账与提案须当场落盘，
使提案审计可立即开始。当前实践中这一步落不了地：架构师在落盘前还要再等一次
「用户同意提案」，而提案正文彼时尚不存在，Reviewer 与 PM 在仓库里没有任何可
读取的载体，协作链在起点即断，多 agent 体系因此从未真正运行过一次。

## 2. 现状证据

- `tasks/` 目录不存在（`ls tasks/` 实测），全仓 0 份任务台账、0 份提案／设计产物。
- 三段门禁（提案／设计／交付）与两类产物（台账／产物目录）只有规则文本，无一次实际运行记录。
- `13-task-model.md` §7.1 把「用户同意提案」设为 `proposed` 的前置条件，与「不落盘则无人可接手」互相牵制。

## 3. 目标与可验证判据

- 触发：用户下达创建任务 ＋ 架构师确认理解需求。
- 动作：`tasks/T-YYYYMMDD-NNN.md` 与 `tasks/T-YYYYMMDD-NNN/proposal.md` 同轮落盘。
- 判据一：落盘后仅凭仓库文件即可发起 `proposed -> proposed-reviewed`，无需读取对话上下文。
- 判据二：台账 `status:` 行的取值在 `13` §2 状态表内合法。
- 判据三：本任务自身即为该规则的首次实弹验证。

## 4. 边界与限制

- 本提案不含设计方案：如何修订 `13` §7.1、§6 表与状态记录形制，属设计段（`design.md`）。
- 台账首条记录行的旧状态字面量（此处用 `—>`）尚无规则规定，须由审计或 PM 裁定形制。
- 任务台账建立时点未写入 `13` §6 交付物表，属已知余量。
