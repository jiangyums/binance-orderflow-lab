## 发现

### P1 — 提案声明的范围与实际目标及交付范围不一致

提案 §0 将本任务界定为 `updated_at` 取值、自指义务、记录形制与判据封闭，并声明新增的载体编码缺陷只作为证据、不扩展议题。但 §3 G-5 将 UTF-8、NUL 和 EOL 规范列为独立目标，§4 D-7 将其列为待裁规则事项，§8 J-8 又要求其成为交付验收判据；台账 `output_contracts` 也包含相应治理文本约束。提案的边界声明与其目标、决策项及验收范围相冲突。

### P1 — 提案内容越过提案段的范围

`13` §2.1 将提案限定为回答「是否值得做」，不包含设计／实现方案。本提案 §4 已提出具体规则选项和取值语义，涉及 Git 查询、字段权威性、具体章节落点及修改形制；§8 列出具体的实现后验收操作与判定。这些内容已形成详细设计与验证方案，不仅是对任务价值、目标和风险的说明。

### P1 — `updated_at` 的两个候选谓词都未实现目标所要求的唯一、可判取值

提案 §3 G-1 要求唯一且可复算的取值谓词，但 §4 D-1 的甲只把 Git 命令输出作为派生读数，同时称台账字段字面值仅作展示、审计不比对该字段；§8 J-1/J-3 所述复算检查只验证 Git 命令输出对应其选中的提交时间，未验证台账 `updated_at` 字段本身。乙则允许字段等于提交链中「某一」既有提交的 committer 时间，没有限定必须选哪一提交或其与最后更新时间的关系，因而容许多个不同字段值。两种备选均未给出满足 G-1 的单一字段取值判据。

### P1 — 判据封闭目标未定义未覆盖发现的可执行流程

提案 §3 G-4 将「没有已批准判据来源」设为不得作为 `rejected`／`blocked` 依据，同时 §7 R-2 仅称可记为观察并补充判据。提案未定义此类观察的归属、必须完成的状态或流程，也未说明在提案审计阶段出现重大但未列入既有判据的问题时，如何确保它得到处理。该目标可能使审计发现无法形成可执行的后续处置。
